# Дизайн: калибровочный набор лаборатории (spec_02 … spec_05)

Дата: 2026-10-28. Статус: **проект, ожидает утверждения владельцем**.
Ветка: `calibration-suite` = `origin/main` (5d94e97) + cherry-pick фикса журнала (f2d6119).
Продолжает нумерацию после `spec01-two-sided-momentum`.

## 1. Intent и цели

Цель набора — **не найти альфу, а натренировать и проверить саму лабораторию** на
классах стратегий, которых она ещё не видела. Четыре спеки упорядочены от null-теста
к адверсариальному стресс-тесту ядра:

| Спека | Черновое имя | Класс | Что проверяет впервые |
|---|---|---|---|
| spec_02 | B | buy & hold (0 параметров) | вырожденный путь отчётности: n=1 сделка, PF null, фолды с одним баром-эпизодом |
| spec_03 | A | MA crossover (низкая частота, без стопов) | сигнал-ориентированный выход без стопа, sparse-очередь flip'ов, столкновение с гейтом выборки G1 |
| spec_04 | C | limit-pullback (maker-вход) | очередь pending-лимиток: неисполнившиеся, срок жизни, maker-комиссия, поведение на вилке fork |
| spec_05 | E | DCA-сетка без стопа (анти-стратегия) | equity < 0: гейт `equity<=0`, отсутствие стопа уровня счёта, недостижимость ликвидации при leverage=1 |

Успех = каждый прогон интерпретируем и **механические verification-критерии (часть 2,
раздел 4) пройдены**; проваленные стандартные гейты — штатный вывод, а не авария.
Провал части 2 = дефект лаборатории = главная находка, публикуется как есть.

## 2. Не-цели и анти-цели

- Не целим в прибыль, PF, sharpe — это калибровка инструмента, каждая спека помечена
  «калибровочная, не alpha-претензия».
- **Не чиним ядро по ходу прогонов** (особенно E): дефекты только регистрируем; fix —
  отдельная работа, как было с `entry_price`.
- Не трогаем holdout/live. Все прогоны — только fit-окно. Каждое касание истории
  фиксируется в `data/touch_registry.json` (сейчас файла нет — значит касаний 0, и так и пишем).
- Анти-цель: не подгонять гейты/параметры после взгляда на данные. Всё ниже
  pre-registered до первого прогона; правки после данных допускаются только как
  явно помеченный второй exploratory-прогон.

## 4. Двухчастные критерии приёмки (ключевое решение дизайна)

В каждой спеке до данных фиксируются ДВА независимых набора:

**(1) Стандартные гейты лаборатории — без изменений** (из чек-листа
`strategydocs/отчёт_протестировано_3_спеков_20261022.md`):
- G1: ≥100 сделок на инструмент в fit, ≥300 агрегировано;
- G2: ≤3 свободных параметра с экономическим смыслом, грубая не-коллинеарная сетка;
- G3: медианный PF сетки ≥1.15, центр ≥1.3; >30% падение PF при шаге сетки — kill;
- G4: PF ≥1.3 net при двойной комиссии (2×taker + 2×slip), не maker;
- G5: ≥2 инструмента, знак P&L положителен в ≥2 из 3 календарных фолдов.

Публикуем вердикт честно, даже ожидаемо-красный. Провал (1) = вывод об экономике
класса или о предвзятости самих гейтов — норма жизни, не баг.

**(2) Verification criteria — механические сверки конвейера.** Это настоящая приёмка
калибровки: независимый скрипт пересчитывает ожидаемое по тем же данным и публичным
константам, сверяет цифра-в-цифру (tolerance объявлен в каждой спеке). Провал (2) =
дефект лаборатории: регистрируется в отчёте с минимум-репро и пушится.

Правило интерпретации (заранее): «зелёная часть 2 + красная часть 1» = лаборатория
исправна, класс экономически мёртв. «Красная часть 2» = чинить лабораторию, выводы о
классе не делать вообще.

Ниже — спеки. Параметр/сетка/критерии заморожены этим документом.

## 5. spec_02 — buy & hold (B): null-тест конвейера

**Гипотеза для лаборатории:** вырожденный путь (0 свободных параметров, 1 эпизод на
инструмент) проходит весь конвейер — warmup, run, обе вилки, метрики с null PF, CSV,
фолды — без падений и с числами, считаемыми руками.

**Стратегия:** существующая `buy_hold` (`strategylab/strategy/examples.py`): один
MARKET BUY quantity=1 на первом баре, закрытие — ответственность движка на конце окна.
**Премиса этой секции про margin-cap не подтвердилась кодом** (проверено чтением
`broker/sim.py` до прогона, builder-check 2026-10-28): у брокера нет проверки маржи —
`buy_hold` с qty=1 BTC (нотионал ~11× капитала при ~114k) откроется как есть. Это
**finding №0 спеки B, зарегистрированный до данных**: env-design §9.3 объявлял
margin-check обязательным, ядро его не реализует. V2.2 считает аналитику при qty=1
сырой; скрипт пишет независимо от движка.

**Сетка:** одна ячейка (параметров нет). G2/G3 неприменимы — помечаем N/A в отчёте
явно, а не молча.

**Verification (часть 2), tolerance: точное равенство Decimal кроме допущения ±1 бар на
исполнение:**
- V2.1: ровно 1 сделка на инструмент; вход — close **второго бара** окна ×(1+slip)
  (правило движка: ордер с сигнала на баре 0 исполняется на apply_bar бара 1),
  taker-fee; выход — close последнего бара окна ×(1−slip), taker-fee.
- V2.2: net P&L == аналитическая реконструкция из баров БД: `qty·(exit−entry) −
  entry·qty·taker − exit·qty·taker` (qty=1 — см. finding №0 выше). Сверка скриптом,
  читающим SQLite напрямую.
- V2.3: вырожденная статистика сериализуется без исключений: при одной убыточной
  сделке `profit_factor == 0` (не null!), `sharpe == null` (n<2), `win_rate` числится;
  CSV-запись харнесса и `build_report`-рендер (дампит `..._report_p.txt`) обязаны это
  пережить — проверяется прогоном, а не только тестом.
- V2.4: знак net предсказуем заранее — сверять не с «close[0]», а с фактическими
  исполняемыми барами: если `h[-1]·(1−slip) < h[1]·(1+slip)` (выходной close ниже
  входного с учётом slip/комиссий), net обязан быть отрицательным; противоречие =
  дефект. (Брат-ревью A10(i): «наоборот» из close[0]/close[−1] арифметически не
  следует, вход — бар 1.)

**Ожидаемый вердикт гейтов (pre-registered):** G1 ❌ (1 сделка), G4/G5 ❌ по знаку на
up-рынке — неважен; публикация красной таблицы и есть тест честности отчётности.

## 6. spec_03 — MA crossover (A): медленный класс и предвзятость G1

**Гипотеза для лаборатории:** низкочастотный **нет-стопный** класс: единственный выход —
переворот сигнала либо конец окна. **Поправка после брат-ревью (owner-approved
2026-10-28, до данных, A1):** премиса «SELL на кресте смерти открывает шорт» опровергнута
кодом — равновеликий противоположный филл ОБНУЛЯЕТ позицию без флипа (`position.py:65-72`,
флип только при `fill.qty > qty`, `position.py:73-82`). Значит `sma_cross` — класс
long/flat (или short/flat, если первый кросс — death): сторона постоянна на прогон,
двустороннего flip-класса в лаборатории нет — это регистрируется в отчёте как
kernel-finding (Андрею важно: его spec_01 назывался two-sided). Проверяем: sparse-эпизоды,
длинный разогрев (slow=200 баров ≈ 8.3 суток), полный аналитический реплей журнала, и
главное — честный ответ лаборатории: убивает ли G1 медленные классы по построению.

**Стратегия:** существующая `sma_cross` (fast/slow обязательны, дефолтов нет).
**Параметры (2 свободных, ≤3 ✓):** fast ∈ {20, 50}, slow ∈ {100, 200}; сетка 4 ячейки,
fast<slow во всех. Интервал 1h.

**Verification:**
- V3.1 (перепиннен по поправке премисы): K = число пересечений SMA (golden+death),
  посчитанное независимым скриптом по часовым закрытиям из БД с тем же warmup-правилом,
  НО только кроссы на барах, кроме последнего (сигнал последнего бара не исполняется —
  правило «ордер бара N живёт с N+1»). Ожидаемое число строк журнала == ceil(K/2):
  нечётный кросс открывает эпизод, следующий чётный закрывает (обнуление без флипа),
  висящий последний эпизод сводит окно. Допуск 0; K=0 ⟹ 0 строк, net=0.
- V3.2: в журнале ни одной строки с причиной выхода «stop/take-profit»; все выходы —
  market-филл переворота, последний — window-close.
- V3.3 (по правленной premisse — прежняя «side-атрибуция long+short» вырождается):
  полный по-сделочный реплей: сторона всех эпизодов = сторона первого кросса; для
  каждого эпизода скрипт аналитически считает entry/exit ts и цены (close бара кросса,
  исполнение на +1 баре с slip по направлению, taker-комиссии с обоих концов,
  финальный выход — сведение окном) и сверяет с журналом цифра-в-цифру (допуск
  1E-20); сумма pnl журнала == net из CSV.
- V3.4: **инвариант вилок:** стратегия не выставляет внутрибарных уровней → PESSIMISTIC
  и OPTIMISTIC обязаны совпасть побайтово по метрикам и журналу прогона (рендер-тексты
  вилок легитимно различаются строкой `intrabar:` — сравнение не по ним). Расхождение
  в числах = дефект форка.

**Ожидаемый вердикт гейтов:** G1 ❌ по всем ячейкам. Замер до данных (брат-ревью по БД,
2026-10-28): пересечений 51–110 на ячейку за 333 дня — не «10–40», как предполагалось
(оценка дизайнера ошиблась в 2.5–3× — тоже материал калибровки); строк журнала
ceil(K/2) = 26–55 < 100, так что ❌ сохраняется и после поправки премисы. Этот ❌ и
есть предмет исследования: в отчёте — измеренная частота vs порог 100, вывод «гейт
выборки предвзят к классам чаще N сделок/год», с формулировкой для владельца.

## 7. spec_04 — limit-pullback (C): maker-механика

**Гипотеза для лаборатории:** впервые в проде идут пассивные ордеры: очередь pending,
срок жизни лимитки, неисполнившиеся и снятые ордера, maker-fee на входе, взаимодействие
с конец-окна. Плюс замер тонкого льда: как лимитки живут на pessimistic vs optimistic.

**Стратегия:** новая `limit_pullback` (модуль `strategylab/strategy/limit_pullback.py`,
регистрация в `STRATEGY_CLASSES`/`build`, юнит-тесты как у остальных — план определит).
Логика (заморожена): лимитки ставятся **несовместными волнами**, чтобы в брокере не
копилась лестница BUY-лимиток, наполняющая позицию каскадом падения: на баре, когда
флэт и `bar_index ≡ 0 (mod e)`, выставляется один LIMIT BUY по `close·(1−d)` c
`expires_in_bars = e`; исполнение — когда low бара касается цены (по цене лимита,
maker-fee); не исполнилась за `e` баров — снимается expiry-фичей. Исполненная позиция
живёт `H` баров без стопов/тейков и закрывается MARKET SELL reduce_only (taker+slip);
пока позиция открыта, новых волн нет. (Решение о волнах — уточнение к утверждённому
дизайну: «заявка на каждом флэт-баре» при живой очереди лимиток = молчаливый grid,
это ломало бы V4.1/V4.3.)

Брат-ревью уточнило (owner-approved 2026-10-28): при периоде волн, равном ttl, на
границе волны (бар, кратный e) старая лимитка ещё не списана — списание происходит на
входе следующего `apply_bar` — и в очереди транзенторно стоят две entry-лимитки.
Двойного филла не существует: для старой это последний исполнимый бар, новой ещё нет
«хода» (исполняется не раньше следующего бара). Значит проверяемый инвариант —
«не более одной ИСПОЛНИМОЙ entry-лимитки на баре», а не «≤1 в очереди».

**Предпосылка (решение владельца, 2026-10-28):** ядро не умеет снимать неисполнившиеся
лимитки — у `Order` нет поля TIF/expiry, cancel-API нет, а reduce-only-трюк ломается о
`_cancel_reduced` (снимает все reduce-only ордера при флэте). Поэтому spec_04 требует
маленькой **фичи** ядра: expiry лимитки в барах. Он оформляется **отдельной веткой
`feat/limit-order-expiry`** (база — `calibration-suite`) в репо Андрея, с объяснительной
запиской в `strategydocs/` (зачем нужна, семантика, совместимость), и пушится туда
самостоятельно — Андрей может ревьюить/мержить/отклонить её независимо от набора.
`calibration-suite` подтягивает фичу merge'ом только для прогонов spec_04. Жёсткие
гарантии «не сломать ядро»: новое поле `Order` со значением по умолчанию None; при
отсутствии expiry поведение побайтово прежнее; весь pytest зелёный **без правок
существующих assert'ов** брокерских тестов; артефакты spec_02/spec_03, перепрогнанные
после merge, побайтово равны baseline (стратегия spec_01 живёт в своей ветке — её
числа гарантирует нетронутый тестовый набор sim). Сам факт
«maker-механику нельзя было проверить» — finding №0 спеки C. Коммит фичи существует
**до** verify-скрипта spec_04 (анти-подгонка).

**Параметры (3 свободных):** d ∈ {0.003, 0.005}; e ∈ {12, 24, 48} баров; H ∈ {24, 48}
баров. Сетка 12 ячеек на инструмент.

**Verification:**
- V4.1: maker-комиссия (0.0002) стоит на каждом входе, taker (0.0006) — только на
  выходах; ни одна сделка не имеет двух taker-лег.
- V4.2 (поправка по коду, брат-ревью A2: `_close_window` очередь НЕ снимает — «движок
  обязан снять» было премисой не из кода): артефакт делит финальную очередь брокера на
  `pending_limit_buy` (живые entry-лимитки, чей ttl-хвост пересёк границу окна) и
  `pending_other` (напр. MARKET-выход, поданный на последнем баре). Независимая машина
  предсказывает обе величины; расхождение = дефект конвейера. Сами пережившие окно
  заявки регистрируются в отчёте как finding движка: «снимает только TTL, конец окна
  очередь не чистит».
- V4.3: независимый пересчёт по БД дисциплины волн: число отправленных лимиток ==
  волны, начавшиеся во флэте (состояние машины пересчитывается скриптом независимо);
  число филлов == бары, где low ≤ цены лимита в течение `e` баров после подачи;
  снятые по expires == разница; `pending_limit_buy` (колонка артефакта, см. V4.2) ==
  лимитки, чей ttl дотянул за границу окна. Допуск: 0 расхождений при правиле «заявка с
  бара N активна с N+1» (оно подтверждено кодом движка до прогона). Машина обязана
  моделировать и транзенторное перекрытие волн (уточнение ниже) — иначе тождество
  разъедется на каждом e-м баре.
- V4.4: fork-расхождение зарегистрировано числом: при отсутствии стопов расхождение
  pessimistic/optimistic обязано быть нулевым; ненулевое = дефект (и это ровно тот
  тонкий лёд, ради которого спека).

**Гейты:** считаются и публикуются; ожидаем G1 близкий к проходу (частые заявки),
G3/G4 — красный (maker-эдж отката ≈ шум). Норм.

## 8. spec_05 — DCA adversarial (E): стресс-тест ядра

**Гипотеза для лаборатории:** намеренно плохая стратегия (усреднение вниз без стопа)
топит equity в минус и проверяет finding записки по ядру «нет стопа уровня счёта,
ликвидация при leverage=1 недостижима» в бою: что делает модель при equity<0 —
продолжает открывать, падает исключением, выдаёт NaN. Отчёт помечается «анти-стратегия,
никогда не торговать живьём».

**Стратегия:** новая `dca_grid` (модуль + реестр + тесты — в плане). Логика (заморожена):
первый MARKET BUY; далее при закрытии бара ниже геометрического уровня
`close_сигнала·(1−s)^k`, k = число уже поданных слоёв — докупка фиксированным лотом
(тот же размер, что первый; лот = 1 единица инструмента, как у эталонных
`buy_hold`/`sma_cross`), не более `L` докупов; стопов,
тейков, переворотов нет; закрытие — конец окна. **Поправка (owner-approved

## 10. Что остаётся билдеру (план, не угадывание)

- Артефакты прогона (решение из builder-check): существующий CSV `sweep.py` — только
  метрики, без филлов, а `run_fork` не отдаёт наружу брокера — поэтому верификации
  пишут новый харнесс `scripts/calib/`: он собирает `ReplayDriver + BrokerSimulator +
  Engine + TradeLog` напрямую (эквивалентность `run_fork` пиннится тестом), дампит
  журнал сделок, `pending_after` (снимок очереди брокера после последнего бара),
  метрики каждой ячейки в размеченный UTF-8 CSV. `cli.py`/`sweep.py` не трогаем.
  Схема артефактов замораживается коммитом **до** первого прогона.
- Схема CSV-строки ячейки (зафиксирована после брат-ревью A2/A7, до коммита харнесса;
  без этих колонок часть сверок механически невыводима):
  `fork, spec_version, <params...>, trades, wins, win_rate, net_pnl, equity,
  max_drawdown, profit_factor, sharpe, pending_limit_buy, pending_other`
  (`win_rate` = wins/trades, при 0 сделках — `null`; pending-разбивка: не reduce-only
  LIMIT = limit_buy, прочее = other; счётчики списаний не нужны — экзотика закрывается
  тождеством V4.3). Плюс харнесс дампит `build_report`-текст пессимистичной стороны в
  `..._report_p.txt` — вырожденный рендер (null PF/sharpe при n=1) проверяется на
  реальных данных, а не только в тесте-эквивалентности.
- `ensure_fit` строгий (A9): прогон разрешён только при `zones_touched == (Zone.FIT,)`;
  пустое множество зон (окно без разметки) — тоже `OutsideFitZone`. Иначе опечатка в
  start_ts тихонько прогнала бы 2024-й BTC «вне протокола» с touches 0 на бумаге.
- Точные имена модулей/классов/тестов для `limit_pullback` и `dca_grid` (и для фичи
  ядра expiry/cancel из spec_04), порядок коммитов, чек-лист прогонов.
- Форму verify-скриптов: `scripts/calib/` по одному на спеку; читают БД **сырым
  `sqlite3`** со своим bucketing'ом часов, без единого импорта `strategylab` (A8:
  иначе сверка наследует баги той самой агрегации/зон, которую верифицирует), и
  читают артефакты прогона. Sanity-константы по БД (7 992 полных часовых группы BTC/ETH
  в окне, 0 гэпов) — из замеров брат-ревью, зафиксированы здесь.
- Ничего из параметров/критериев/гейтов выше не меняется; при противоречии критерия с
  реальностью кода движка — стоп, вопрос владельцу, не тихая правка.
