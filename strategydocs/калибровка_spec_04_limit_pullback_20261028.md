# Калибровка spec_04 — limit_pullback: maker-механика в первом живом прогоне (2026-10-28)

**Калибровочный прогон лаборатории, не alpha-претензия.** Ядро (`strategylab/`) не
трогалось посреди прогона (правило E): дефекты и особенности регистрируются, не
чинятся. Сам TIF-механизм смёржен в ядро заранее, на Task 4 (`feat/limit-order-expiry`,
коммиты `c5b0cb0` → merge `6663297`), и для этого спека заморожен.

## Условия прогона (заморожены, design §3 + §7)

- Окно fit: `[1761523200, 1790294400)` = 7 992 полных часовых группы, 0 гэпов
  (перепроверено независимым чтением SQLite).
- Сетка: `depth ∈ {0.003, 0.005}`, `ttl_bars ∈ {12, 24, 48}`, `hold_bars ∈ {24, 48}`
  → 12 ячеек × 2 символа; связей между параметрами нет, `отклонено: 0` (R6 не сработал).
- Капитал 10 000; издержки `taker_fee=0.0006 maker_fee=0.0002 slippage=0.0005 leverage=1`.
- `spec_version`: 24 пина пересчитаны stdlib ДО прогона (канонический JSON по
  `spec.py`) и заморожены в verify-коммите `efdb854` **до первого прогона сетки**;
  совпали в csv обеих вилок и каждой journal-строке всех 24 ячеек.
- Вилки PESSIMISTIC/OPTIMISTIC: у limit-only стратегии нет внутрибарных споров →
  журналы совпали побайтово (V4.4). `touches: holdout=0, live=0`; реестр касаний
  отсутствует.
- Артефакты: `data/calib/limit_pullback_*` — 2 сетки полного окна, 6 фолдов,
  2 прогона `--double-costs` (центральная ячейка 0.005/24/48).
- Fresh-eyes ревьюер (новая сессия; критерии независимо выведены из текста design §7
  и кода ядра ДО чтения машины) дал APPROVE-FREEZE: 24 пина пересчитаны заново —
  0 расхождений; мутационная батарея поймана машиной полностью — TIF off-by-one
  (18 ячеек V4.1), off-by-one выхода (`≥`→`>`, 24), перестановка pending-колонок (48),
  force-close без slip (12).

## Часть 2 — verification V4.1–V4.4 (замороженный скрипт, 100/100 PASS)

`scripts/calib/verify_spec04.py` запинен коммитом `efdb854` ДО первого прогона сетки;
первый запуск и перезапуск после прогонов фолдов/DC дали один результат — 100×PASS,
exit 0. Ноль импортов из `strategylab`: своё часовое агрегирование (close — последняя
минута бакета, low — минимум бакета, шаги строго по 60 с), свои Decimal-константы
design §3, свои пины spec_version.

Машина состояний по бару воспроизводит семантику ядра (ревьюер вывел её из
`engine.py`/`sim.py` независимо): на входе `apply_bar(i)` молчаливое списание заявок с
`i ≥ w+e+1`; лимтка исполнима на барах `w+1…w+e` при `low ≤ limit` по цене лимита;
MARKET-выход, поданный на баре X, исполняется на X+1 по `close·(1−slip)`; открытая
позиция в конце окна сводится движком напрямую (не филл брокера) на последнем баре.
Транзенторное перекрытие волн (A3: подача новой на баре `w+e` при живой старой)
смоделировано очередями — иначе тождество V4.3 съезжало бы на каждом e-м баре.

- **V4.1** PASS ×24: полный построчный реплей всех 3 203 строк цифра-в-цифру (ts, цены,
  pnl; допуск 1E-20); entry — ровно цена лимита **без slip** (maker-вход) во всех
  сделках; формула `(exit − entry) − maker·entry − taker·exit` точна; анти-формула
  с taker на входе ни разу не совпала (расхождение = 0.0004·entry > 0 — проверка
  невырождена); Σpnl == колонка `net_pnl`.
- **V4.2** PASS ×24: `pending_limit_buy == 0` и `pending_other == 0` во всех ячейках
  полного окна — машина предсказала ровно 0, артефакты подтвердили. Реальный
  переживший окно ордер поймался в **фолде ETH 1** (`pending_limit_buy = 1`): лимитка
  волны бара 2640 не была тронута и её TTL-хвост пересёк границу фолда — см. finding.
- **V4.3** PASS ×24: счётные тождества с допуском 0: `submits == fills + expired +
  pending` (сетка: 3 930 = 3 203 + 727 + 0), `expired == submits − fills −
  pending_limit_buy(csv)`, entry-fills == строк journal, hold-выходы == строки −
  window-close (висящих сводов окна — 13 из 24), колонка `trades` == строки обеих вилок.
- **V4.4** PASS ×24: файлы журналов pess/opt побайтово равны (целиком), метрики csv
  равны всеми колонками кроме `fork` — премиса design «расхождения вилок нет без
  внутрибарных споров» подтверждена на limit-классе живыми данными.
- **version/attribution** PASS: 24 пина совпали в обеих вилках; journal-строк с чужим
  spec_version нет; `combination` парсился key=value (R5) и соответствовал ячейке.
- Честная пометка (от ревьюера): лишние заявки, которые движок подал бы, но они не
  исполнились бы и не пережили окно, для артефактов невидимы — `expired` существует
  только в пересчёте машины, из артефактов проверяется лишь непротивленность
  тождеств. Регистрируется как принципиальное ограничение verify, не дефект скрипта.

## Что показала maker-механика (секция для свода Task 9)

- **TIF в проде сработал 727 раз** — столько заявок молча списались по `expires_at`
  на входе apply_bar по всей сетке (18.5% из 3 930 подач). Ветка `feat/limit-order-expiry`
  (Task 4) прошла первый живой прогон с нулевым расхождением против независимой машины.
- **Touch-rate убывает с глубиной лимитки**: d=0.003 → 86.4% филлов (1 648/1 908),
  d=0.005 → 76.9% (1 555/2 022); по символам BTC 79.8%, ETH 83.2%.
  Экономика согласуется: дальше от цены — реже исполняется.
- **Дисциплина несовместных волн держится**: подач меньше числа слотов `i ≡ 0 (mod e)`
  ровно на бары с открытой позицией (например BTC 0.005/48/48: 90 подач из 167 слотов) —
  лестницы BUY-лимиток брокер не накопил, перекоса очереди каскадом падения не случилось.
- **Очередь конца окна не чистится (finding движка, поправка A2 подтверждена живьём)**:
  `_close_window` сводит позицию, но НЕ снимает заявки. На полном окне фаза сетки не
  подкинула ни одного выжившего (pending 0/0 во всех 24 ячейках), а на фолде ETH 1
  выжившая лимитка зафиксирована в артефакте (`pending_limit_buy = 1`). В проде это
  означает: ордера остались бы висеть на бирже после окончания окна. Регистрируем,
  не чиним (правило E); кандидат в backlog ядра — `cancel_all` на границе окна.
- **Комиссии посчитаны понемногу, как обещано**: maker 0.0002 заплачен на каждом из
  3 203 входов (25 296.686), taker 0.0006 — только на выходах (75 721.780); две taker-ноги
  не встретились ни в одной сделке (анти-формула V4.1). Скидка maker-входа против
  all-taker контрфактического прогона — 50 593.373 (≈15.79 на сделку), ещё ≈63 101 —
  цена-издержки слипиджа, уже сидящие в gross (входы его не платят — лимитка).
- **Ноedge это не купило**: net −381 484 при gross −280 466 — потери в цене (ловля
  отскоков, которая их не поймала), а не в комиссиях; удвоение издержек добавило
  −10 251 BTC / −320 ETH к центральному net. Pre-registered гипотеза «maker edge на
  pullback ≈ 0» подтверждена.
- **Отрицательный equity BTC** (центр: −27 000.56 при капитале 10 000) — продолжение
  Finding №0 из spec_03: нет проверки margin/notional при подаче, liquidation при
  leverage=1 недостижим (нужен `bar.low ≤ 0`) — за 7 992 bars × 24 ячейки × 2 вилки
  `LiquidationError` не сработал ни разу, что и ожидалось. Для spec_05 (dca_grid,
  лот 1 BTC) учтено в pre-регистрации V5.3/V5.4.
- **Мелочь ядра (kind-agnostic списание)**: фильтр `expires is not None` на входе
  apply_bar не различает вид ордера — сегодня безопасно (TIF ставится только entry-
  лимиткам), но если TTL когда-нибудь получат MARKET/reduce-only — они спишутся тем же
  молчаливым механизмом. Не дефект этого прогона, зарегистрировать в Task 9.

## Kernel-findings для Task 9

1. Очередь брокера переживает конец окна (ETH fold1: pending_limit_buy=1) — снять
   вопрос либо `cancel_all` в `_close_window`, либо явным прогоном «окно ⊂ очередь»
   в спецификации рантайма.
2. Liquidation/margin проверки отсутствуют (подтверждён на maker-классе, второй спек
   подряд) — актуально для dca_grid с лотом 1 BTC.
3. Silent write-off не оставляет артефактного следа (виден только как расхождение
   независимого пересчёта) — для проде-логов стоит записывать факт снятия заявки.
4. Slip-ассиметрия maker/taker подтверждена понемногу: entry без slip, exit со slip —
   расчёт V4.1 точен во всех 3 203 сделках.
