# Design: R3-C ступень (a) — funding-данные (ветка `feat/funding-data`)

Статус: ЧЕРНОВИК для owner-approve (R-next-4). Владелец одобрил направление R3-C
(funding/carry — первая ветвь предрегистрированной вилки spec_01 «смена класса
идей (carry/structural)») 2026-10-29; этот дизайн — только ступень (a) ДАННЫЕ.

## Зачем
Класс carry неизмерим на OHLCV в принципе — funding-ставки это единственный
источник. Ступень (a) даёт данные; ступень (b) — док-замеры брата с
пререгистрацией (без харнесса, напрямую по БД); ступень (c) — фича-ветка
харнесса (aux-серия + funding в cost model) ТОЛЬКО если ячейка выживет в (b).

## Факты источника (проверено живым запросом 2026-10-29)
- Endpoint: `GET https://fapi.binance.com/fapi/v1/fundingRate`
  (params: symbol, startTime, endTime, limit ≤ 1000). Достижим с этой машины.
- Ответ: symbol, fundingTime (мс, бывает джиттер +3мс → floor до секунд),
  fundingRate (строка), markPrice (строка), rateType.
- Периодичность: каждые 8ч (00/08/16 UTC → ts % 28800 == 0).
- Объём: BTCUSDT от 1704067200 (старт bars_1m) ≈ 2.4k строк; ETHUSDT от
  1761523200 (старт ETH bars) ≈ 1.1k строк. 1–2 пагинационных вызова на символ.

## Хранилище
- Таблица `funding_8h` в существующих `data/btcusdt.db` и `data/ethusdt.db`
  (БД git-НЕ трекаются — локальный артефакт, как bars_1m).
- Схема: `symbol TEXT NOT NULL, ts INTEGER NOT NULL (секунды = fundingTime//1000),
  rate TEXT NOT NULL (Decimal-строка — конвенция bars_1m), mark_price TEXT,
  rate_type TEXT, PRIMARY KEY (symbol, ts)`.
- БЕЗ zone-колонки: сырое зеркало биржи; зонная дисциплина (R-next-2) живёт в
  запросах замеров, не в хранилище. Границы зон задокументировать в докстринге
  загрузчика. Покрытие: от старта bars символа до момента загрузки (включая
  holdout/live отрезок — ХРАНИТСЯ, но НЕ ЗАПРАШИВАЕТСЯ замерами; прецедент bars_1m).

## Загрузчик: `scripts/funding/fetch_funding.py` (новый каталог)
- Только stdlib (urllib.request, sqlite3, json, decimal) — ноль новых зависимостей.
- Идемпотентен: INSERT OR REPLACE по PK; повторный запуск сходится к тому же содержимому.
- Rate-limit: limit=1000, пауза между вызовами; startTime-пагинация по fundingTime.
- Встроенная валидация (провал → exit ≠ 0, явное сообщение):
  1. Непрерывность: нет гэпов > 8ч внутри [start, last] (найдена аномалия → report + stop).
  2. Sanity: |rate| ≤ 0.05 (свободный guard от ошибок парсинга; реальные капы биржи ниже).
  3. Счётчик: rows ≥ expected(8h-сетка) × 0.98.
  4. Выравнивание: ts % 28800 == 0 у всех строк (после floor мс-джиттера).
- Provenance: JSON-сводка в stdout (endpoint, params, rows, min/max ts, время
  загрузки) — факт загрузки цитируется в отчёте замеров. Флаг `--dry-run`
  (загрузка + валидация без записи) и `--report <path>`.

## Тесты
- Unit на фиксатурах записанных JSON-ответов (в тестах сети НЕТ): парсер,
  floor мс-джиттера, валидаторы (гэп, |rate|, выравнивание, счётчик),
  идемпотентность INSERT OR REPLACE.
- Живая загрузка — ручной шаг исполнителя (не CI); provenance-JSON приложить
  к описанию коммита/ветки.

## Чего в этой ветке НЕТ
- Никаких изменений engine/harness/стратегий/CostModel.
- Никаких замеров сигналов (ступень (b) — только после merge, письмом брату,
  с пререгистрацией ОДНОЙ ячейки до чисел; R-next-1: брат публикует первым).
- БД не коммитятся (untracked).

## Ступень (b) — preview (не предмет этого approve)
Док-замеры брата по funding (fit + BTC-предыстория; holdout/live не запрашивать):
funding-экстремумы (z/перцентили) → дрейф спота следующие 8/16/24/48ч;
funding-обусловленный моментум; accrual funding как самостоятельная компонента
PnL перп-позиции (наш CostModel funding НЕ моделирует — это предмет ступени (c)).
Все прокси — с честным входом close_{t+1} (постоянный урок фазы 2026-10-29).
